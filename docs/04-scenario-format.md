# Формат сценария: как добавить свой кейс

Сценарий — один JSON в `data/scenarios/`. Ядро не знает сценариев по именам:
новый кейс = новый файл, код не трогается. Валидация (pydantic) объяснит,
чего не хватает, тесты `test_scenarios.py` проверят целостность.

Руками писать JSON не обязательно: экран «Админ» генерирует черновик сценария
по контексту (сфера, тема, роли, персона, сложность, рамки торга, пожелания)
и даёт править его в редакторе с той же валидацией — см. раздел «Контур
администратора» в [`02-architecture.md`](02-architecture.md). Этот документ
нужен, когда правишь черновик или собираешь кейс полностью вручную.

## Скелет

```json
{
  "id": "...", "title": "...", "category": "...", "difficulty": 1..3,
  "summary": "карточка каталога",
  "setting": "сцена: кто, где, какие суммы на кону",
  "player":   { "role", "goal", "batna_text", "batna_score", "facts", "criteria" },
  "opponent": { "name", "role", "persona", "voice", "portrait", "opening",
                "interests", "levers", "irritants", "templates" },
  "issues":   [ "один числовой + опции пакета" ],
  "max_turns": 12,
  "palette":  { "from": "#dfe9e2", "to": "#f4efe4" },
  "events":   [ "вводные посреди партии" ]
}
```

`palette` — два тона сцены: из них интерфейс строит подложку карточки
каталога, портрет-карты брифа и фолбэк фона партии (пока не положен
`scenes/<id>.jpg`). Оценка длительности для брифа (`est_minutes`) считается
бэкендом из `max_turns` — руками её задавать не нужно.

Контент действий-мелочей (подписи кнопок, ремарки, реплики персон, лимиты) —
тоже данные: `data/actions.json`. Эффекты жестов остаются в коде
(`app/engine/actions.py`), потому что ветвятся по персонам и контексту партии.

## Вопросы торга (`issues`)

Числовой (ровно один — главный):

| Поле | Смысл |
|---|---|
| `direction` | `higher_better` / `lower_better` — с точки зрения игрока |
| `player_target` / `player_limit` | цель и предел мандата игрока |
| `opponent_start` / `opponent_limit` | стартовая позиция и предел оппонента |
| `step` | шаг торга: все предложения оппонента лежат на этой сетке |

Пределы сторон образуют ZOPA; проверка `has_zopa` не даст собрать сценарий
без зоны соглашения. Утилита игрока: 0 на его пределе, 100 на цели.

Булевая опция — разменная монета пакета:

- `player_value` — сколько «да» стоит игроку (может быть отрицательным:
  это уступка, которую игрок продаёт);
- `opponent_cost` — во сколько «да» обходится оппоненту (отрицательный —
  оппоненту это выгодно, он будет просить сам);
- `ask_phrase` — типовая формулировка просьбы. Из неё берутся токены для
  распознавания, поэтому пишите так, как скажет живой человек.

Выгодный размен = `player_value` и `opponent_cost` разных знаков или сильно
разной величины: на этом ядро строит Парето-границу и «осталось на столе».

## Интересы, рычаги, раздражители

- **Интерес** — скрытая боль оппонента. `topics` — стемы слов (не словоформы!
  «команд», а не «команда»), по которым вопрос игрока попадает в тему.
  `probe` — готовый вопрос (подсказка режима обучения), `reveal_line` —
  авторская реплика раскрытия (озвучивается всегда дословно).
- **Рычаг** — аргумент, который реально работает. `aspiration_drop` ≤ 0.3 —
  сила; если интерес рычага ещё не вскрыт, эффект вполсилы. `keywords` — стемы
  для эвристики; следите, чтобы ключи разных рычагов не пересекались, иначе
  сработает первый нераскрытый.
- **Раздражитель** — «больная мозоль» персоны: фразы, на которые напряжение
  прыгает сверх обычных правил.

## Персона

`soft` / `positional` / `hard` — задаёт скорость уступок, чувствительность к
давлению и критериям, пороги предупреждения и разрыва (`app/engine/state.py`).
Мягкая персона не предупреждает о напряжении — она тихо выходит; жёсткая на
давление отвечает упрямством.

## Шаблоны реплик

`templates` — запасная озвучка на каждый вид намерения (14 видов, список — в
`test_scenarios.py::NPC_INTENTS`). Плейсхолдеры: `{offer}` — пакет словами,
`{reveal}` — реплика раскрытия. Шаблоны обязаны существовать даже при живой
LLM: на них падает озвучка, если модель недоступна или сочинила лишнее.

## Балансировка

Прежде чем коммитить сценарий, сыграйте его целиком без LLM (эвристики
детерминированы) и проверьте три исхода:

1. сильная линия (вопросы → рычаги → условный пакет) закрывается в ZOPA;
2. давление доводит персону до предупреждения/разрыва;
3. пассивная игра упирается в «время вышло» с финальным предложением.

Образец такой проверки — `test_session.py::test_rent_game_closes_inside_zopa`.
Ключевая математика порога принятия — в `app/engine/npc.py::_respond_to_offer`:
оппонент сравнивает пакет игрока со своей текущей целью, к концу партии допуск
растёт (дедлайн давит), доверие делает финал щедрее.
